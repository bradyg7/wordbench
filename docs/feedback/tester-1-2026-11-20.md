# First external tester: feedback and priorities (2026-11-20)

Ten comments from the first outside tester, ranked for integration. Each one needs a design folder (or a row in an existing one) before it is built, per AGENTS.md. Additional translations are left out on purpose: most are not public domain.

## Priority order

| # | Finding | Kind | Where it goes | Size |
|---|---|---|---|---|
| 1 | The Webster's dictionary only works after running a script | Setup bug: the release lacks a feature | Ship `dictionary.db` in the release, or download it once on first use from the releases repo. This is a release/packaging ticket | S |
| 2 | Learning the app feels like a big task | Onboarding | New design folder `welcome`: a landing page with **Getting started** (short guided tour) and **I know how, take me in**. Covers #3 and #4 below too | L |
| 3 | A landing page with a tutorial or "hop right in" | Onboarding | Part of `welcome` | M |
| 4 | The app opens at Numbers 25 | Default place | Part of `welcome`: a new study opens at a chosen start (Genesis 1:1 or John 1:1), and after that at the place last read. Numbers 25 is probably the developer's own last place, or a default left from development. Check before deciding | S |
| 5 | Pop-ups close only with × | Interaction | Design folder for cards and popovers: click outside closes, Escape closes, and a **Pin** keeps a card open so two can be compared (Lord beside King in the interlinear). A setting chooses *close on outside click* or *close only with ×* | M |
| 6 | The resize handle sits on the Webster's box, not the whole card | Layout bug | Bug fix (`fix/word-card-resize`): put the handle on the outer card | S |
| 7 | Stacked marks: limit the stacking (two at most, or none), and remove a mark where it was added | Marks | Marks design: a decision on the stacking limit, plus **Remove** on the same toolbar that adds a mark | M |
| 8 | The delete-all menu looks odd | Visual bug, maybe display scaling | Get a screenshot, Windows scale % and theme from the tester, then `fix/` | S, needs repro |
| 9 | Download versions on demand so the package stays small | Packaging | The same mechanism as #1 (optional data packs from the releases repo), built for the dictionary first. Translations wait for licensing; public-domain ones (ASV, YLT, WEB) could come later | M, after #1 |
| 10 | Read aloud: free readers, or Speechify | Accessibility | Start with the system voice already in the webview (`speechSynthesis`, free, offline, no package size). Speechify integration needs their API terms checked; leave it for later | M |

### Why this order
- **#1 first**: the feature is already built, and the tester simply can't reach it. It is the cheapest real fix, and it sets up the download mechanism #9 needs.
- **#2–#4 together**: one design (`welcome`) answers three comments, and the tester's main complaint is how hard the app is to learn.
- **#5–#7**: interaction polish on work that already exists. #6 is a quick bug fix that can go in any time.
- **#8**: needs reproduction before anything is done.
- **#9–#10**: new capability. These come after the basics.

## Decisions for the person
1. The default start place for a new study: Genesis 1:1, John 1:1, or the reader's choice on the welcome page.
2. Stacked marks: at most two on one word, or one only.
3. The card pin and the close setting: build both, or the pin only.
4. The dictionary: bundled (a bigger installer) or downloaded on first use.

## Getting findings from other users' copies

Today findings live in each user's own study folder (`findings/`), on their own computer. To receive them here:

**Recommended: "Send to developer" in the app, opt-in, one finding at a time.**
1. In the Findings list, a **Send** button on a finding shows exactly what will be sent: the finding text, app version, OS, and any attached screenshots the user ticks. It never sends notes, pages, highlights or the study folder.
2. On confirm, the app opens a prefilled **GitHub issue** on a public feedback repo (for example `bradyg7/wordbench-feedback`). The fallback is an email draft (`mailto:`) for users without GitHub. Either way the user presses send in their own browser or mail client, so the app holds no credentials and runs no server.
3. Here, a script (`scripts/import-feedback.mjs`) reads the new issues with `gh`, writes each one as a top-level finding Markdown file in a `findings-inbox/` folder in a scratch or design location (never the real study folder), tagged `external` with the reporter's issue number, and leaves the existing findings-review hash and checkpoint behavior untouched.
4. The daily findings review then reads those files with the rest, so external findings are ranked the same way.

**Alternatives considered**
- *An automatic upload endpoint*: smoother, but it needs a server, storage and a privacy policy. Too much for now.
- *Export a .zip of findings that the user emails*: simple, but manual on both ends. It could be the offline fallback.

**Privacy rule for the design:** nothing leaves a user's computer without their pressing Send on a preview of exactly that content.
